# Technical architecture

Module contents are listed by the [ViewerCore map](/Sources/ViewerCore/MAP.md) and
the [repository map](/MAP.md).
This document holds the rules that span them.

## Core and App boundary

- Logic that needs no UI framework belongs in `Sources/ViewerCore/`. The
  `Sources/ViewerApp/` target holds macOS integration and observable state.
- Core is UI-independent so the executable runners can exercise the same logic the
  app uses, without a window. See [verification.md](/docs/technical/verification.md).

## Coordination

- `AppModel`, isolated on the main actor, coordinates the presentation of one
  workspace. `WorkspaceWindowManager` keeps one model per native tab, and the tabs
  share one persistence coordinator.
- Specialized coordinators own the sub-workflows: rendering, editing, diff
  baselines, the tree, and persistence. They return values or events. `AppModel`
  applies them to its published state, and coordinators do not mutate `AppModel`.
- Views send intents to `AppModel` and render what it publishes. Views do not scan
  folders, compile, watch files, or persist state.
- Git is not exposed to the UI. The diff coordinator selects and retrieves the
  baselines. Core compares two in-memory texts and returns a result that does not
  depend on the document format.

## Targets

- `ViewerCore` holds the UI-independent logic (see its [map](/Sources/ViewerCore/MAP.md)).
  `ViewerApp` is the macOS SwiftUI and AppKit layer; logic that needs no UI framework
  belongs in Core.
- `ViewerContractRunner` covers the Markdown adapter and the LaTeX/process pipeline.
  `ViewerFoundationRunner` covers filesystem, tree, tabs, persistence, and editing and
  merge foundations. They give deterministic validation, so tests should not duplicate
  runner logic. They exist because the local toolchain lacks the `Testing` module.
- `ViewerTabPrototype` and `ViewerWindowTabPrototype` are isolated tab prototypes that
  exercise tab behavior independently of the app target.

## Build channels

- A dev build (`scripts/build-app.sh debug`, `restart-app.sh`, `dev-run.sh`) and the
  installed release app (`install-app.sh`) share the bundle id
  `com.bernardopacheco.viewer` on purpose: UserDefaults state and the Accessibility
  permission stay with one app identity. Because of that, the two cannot be told
  apart by bundle id, so the channel is recorded in the bundle.
- `build-app.sh` writes the custom Info.plist key `ViewerBuildChannel` into the copied
  `Contents/Info.plist` (`dev` for debug, `release` for release) before codesigning.
  The source `Resources/Viewer-Info.plist` does not carry the key.
- The installed release app icon (`Viewer.icns`) has a black background, from
  `Viewer-logo.svg`. The dev build's icon (`Viewer-dev.icns`) has an orange background,
  from `Viewer-logo-dev.svg`; the two SVGs differ only in that colour. Both are
  generated by `scripts/generate-icons.sh`. A Finder or Dock that still shows an old icon
  may be using its icon cache.
- The app shows DEV (Dock badge, `DEV` suffix on window titles, header chip) unless the
  value is exactly `release`. A missing key, an empty or other value, or no bundle (a raw
  binary from `swift run`) also shows DEV, so the label fails towards development.
- The rule lives in `BuildChannel` (Core, pure); the single read of the key is
  `BuildChannel.current` in the app target.
- Known gap: the Info.plist write is verified by building the debug bundle only; the release
  bundle path runs the same code with a different value.
